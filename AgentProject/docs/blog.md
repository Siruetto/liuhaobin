# 办公小助手：一个"能说会做"的智能体

代码地址：https://github.com/Siruetto/liuhaobin （本次作业在 `AgentProject/` 目录下）

一句话介绍：用一句自然语言指挥它干活——算数、记待办、读写文件、查天气、看时间。
它不是在"告诉你怎么做"，而是**真的去做**，做完再用人话汇报结果。

## 一、需求描述

**要解决的麻烦**：日常办公的琐事散落在很多地方——算个数要开计算器，记事情要开备忘录，
改个文件要开编辑器，查天气要开浏览器，看时间要掏手机。每件事都很小，但来回切换很烦。

**目标**：做一个命令行 + 网页都能用的助理，接收一句中文指令，自动判断该干什么、
调用对应的工具、把结果说清楚。

我们给自己定了四条底线：

1. **能说**：支持多轮对话，记得住上下文（比如先问"北京天气"，再问"那上海呢"）。
2. **会做**：每个回答背后要么有一次真实的工具调用，要么明确说"这个我还不会"，不许编。
3. **可扩展**：加一个新工具只改一个注册表，不用动规划器。
4. **能离线演示**：没配 API Key、没网也能跑——这是实际做的时候发现最需要的一条，
   因为演示现场不一定有网。

## 二、业务流描述

```
用户一句话
    │
    ▼
Agent.chat()  ── 从 Memory 取出最近 20 轮对话 ──►  规划器
                                                    │
                          ┌─────────────────────────┴──────────────────────┐
                          │                                                │
                  有大模型 API Key                                  没有 Key / --offline
                          │                                                │
              LLM 通过 function calling                        正则把常见说法映射成工具调用
              决定调用哪个工具、传什么参数                          （固定说法，够演示用）
                          │                                                │
                          └─────────────────────────┬──────────────────────┘
                                                    ▼
                                              ToolBox.call()
                              ┌─────────────────────┴─────────────────────┐
                              │                                           │
                        本地直接调用                              MCP 子进程（--mcp）
                        （默认，最快）                          stdio + JSON-RPC，一行一条
                              │                                           │
                              └─────────────────────┬─────────────────────┘
                                                    ▼
                                          工具返回一段文本结果
                                                    ▼
                                    规划器组织成自然语言回答
                                                    ▼
                              写入 Memory（短期历史 + 长期事实）
                                                    ▼
                                      命令行打印 / 网页显示
```

**一个具体的例子**：用户说"把 明天带伞 写到 notes/todo.md"

1. 规划器判断意图是"写文件"，参数 `path=notes/todo.md`、`content=明天带伞`；
2. `file_write` 把路径解析到 `workspace/notes/todo.md`，检查没有 `../`、不是绝对路径；
3. 真的写盘，返回"已写入 notes/todo.md (12 字节)"；
4. 用户看到一句人话，同时 `actions` 里留下了这次调用的记录，网页上会显示"工具: file_write ✓"。

**出错的情况**：如果用户说"写到 ../secret.txt"，工具会拒绝并返回
"只能操作 workspace/ 目录里的文件"。这句话会原样回到对话里——用户知道发生了什么，
程序也不会崩。

## 三、实现说明

### 1. 模块划分

| 文件 | 职责 |
| --- | --- |
| `agent.py` | 命令行入口：交互模式、单条指令、`--offline` / `--mcp` / `--reset` |
| `agent_core.py` | 智能体主体：选规划器、把一轮对话走完、写记忆 |
| `planner.py` | 两种规划器：`LLMPlanner`（function calling）和 `OfflinePlanner`（正则规则） |
| `llm.py` | OpenAI 兼容的 Chat Completions 客户端，只用 `urllib` |
| `tools.py` | 九个工具的实现在这里，同时提供 JSON Schema 和统一注册表 |
| `memory.py` | 多轮对话记忆 + 长期事实，落盘到 `data/memory.json` |
| `mcp_server.py` | MCP 服务端：`initialize` / `tools/list` / `tools/call` |
| `mcp_client.py` | MCP 客户端：把服务端当子进程，对外仍是一套 `schemas()` / `call()` |
| `web_ui.py` | 网页界面，只用标准库 `http.server` |

依赖是单向的：`agent → planner → tools → config`，`mcp_client` 只是另一种 `toolbox`。
规划器不需要知道工具到底在本地还是在 MCP 子进程里跑——这是整个设计里最省事的一点。

### 2. 工具层：一份定义, 三处复用

每个工具只写一次，包含名字、说明、参数 Schema 和处理函数：

```python
{
    "name": "calculator",
    "description": "计算数学表达式, 支持 + - * / // % ** 和括号。",
    "input_schema": {...},
    "handler": calculate,
}
```

这一份定义被三处用到：

* 转成大模型 function calling 的 `tools` 参数（`tool_schemas()`）；
* 转成 MCP `tools/list` 的返回（`mcp_tool_schemas()`）；
* 单元测试直接拿它检查每个工具都有名字和 Schema。

加一个新工具（比如"翻译"）只需要往 `TOOLS` 列表里加一项，规划器、MCP、网页都不用改。

### 3. 为什么要做离线模式

一开始只写了大模型版本，后来发现两个问题：演示现场不一定有网；没配 Key 的人跑不起来，
连"这个项目能干什么"都看不到。于是加了一个 `OfflinePlanner`：

用正则把常见说法映射到工具调用，比如"记一下 X"→`todo_add`、"几点了"→`current_time`、
"把 X 写到 Y"→`file_write`。它只认固定说法，但足够把整条链路演示完整。

顺带还实现了两个小能力：**记住名字**（"我叫刘浩彬"→"我叫什么"）和**追问城市**
（先问"北京天气"，再说"那上海呢"）——这两个都是多轮记忆的体现。

### 4. MCP 是怎么接的

MCP 的 stdio 传输就是"一行一条 JSON-RPC 消息"：

```json
{"jsonrpc":"2.0","id":1,"method":"initialize"}
{"jsonrpc":"2.0","id":2,"method":"tools/list"}
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"calculator","arguments":{"expression":"2+3"}}}
```

服务端实现三个核心方法就够了，`tools/call` 的返回按 MCP 约定包成
`{"content":[{"type":"text","text":"..."}],"isError":false}`。
客户端用 `subprocess.Popen` 起服务，把 stdin/stdout 当管道，读写都用 UTF-8 字节，
避免 Windows 控制台编码把中文参数弄坏。

工具在子进程里执行的另一个好处是**隔离**：即使某个工具把进程搞挂了，主程序也只是收到
"MCP 服务没有响应"，不会跟着一起崩。

### 5. 安全上的几个处理

* 计算器**不用 `eval`**：用 `ast.parse` 拿到语法树，只允许数字常量和四则运算节点，
  `__import__("os").system(...)` 这种输入会直接报错；指数还限了上限，防止 `9**9**9` 卡死。
* 文件工具只能操作 `workspace/`：相对路径会被 `realpath` 解析后和根目录比对，
  `../` 和绝对路径都会被拒绝。
* 所有工具失败都抛 `ToolError`，由上层变成一句人话；工具出错不会让对话崩掉。

### 6. 记忆

* **短期**：最近 20 轮对话，每次请求都带给模型；
* **长期**：键值事实（名字、常去的城市），存 `data/memory.json`，重启还在。

### 7. 测试

51 个单元测试，四大类：工具行为（计算器、待办、文件、天气、时间）、离线规划器的意图识别、
MCP 协议（服务端处理 + 客户端子进程往返）、智能体端到端（对话、记忆、重置）。
天气相关的测试用 mock 替换网络请求，所以**整套测试不需要联网**。

## 四、使用示例

### 1. 命令行（离线模式，不需要 Key）

```text
> python agent.py "帮我算一下 (3+5)*2"
16

> python agent.py "记一下 周五前交周报"
已记下第 1 条待办: 周五前交周报

> python agent.py "看看待办"
待办清单:
1. [ ] 周五前交周报

> python agent.py "把 会议改到周三 写到 notes/todo.md"
已写入 notes/todo.md (24 字节)

> python agent.py "读一下 notes/todo.md"
会议改到周三

> python agent.py "现在几点"
2026-10-19 11:17:49 (星期一)

> python agent.py "我叫刘浩彬"
记住了, 你叫刘浩彬。

> python agent.py "我叫什么"
你叫刘浩彬。
```

### 2. 走 MCP

```text
> python agent.py --mcp "现在几点"
2026-10-19 11:17:50 (星期一)
  [工具] current_time({}) -> ok
```

### 3. 网页界面

```bash
python web_ui.py --port 8000
```

打开 <http://127.0.0.1:8000>，输入框里说一句话，右边会显示这次调用了哪个工具。
页面是单文件 HTML + `fetch`，后端是标准库 `http.server`，没有任何前端依赖。

### 4. 大模型模式

```bash
$env:AGENT_API_KEY="sk-xxx"
$env:AGENT_BASE_URL="https://dashscope.aliyuncs.com/compatible-mode/v1"
$env:AGENT_MODEL="qwen-plus"
python agent.py
```

这时可以随便说，比如"帮我看一下北京天气，然后记一下明天带伞"——
模型会自己拆成两次工具调用。

## 七、成员心得

**刘浩彬**：这次最大的收获是"工具调用的边界在哪里"。一开始我以为只要把工具交给模型，
它自己会用好；实际写下来才发现，**模型负责决定"做什么"，代码负责守住"不能做什么"**——
路径不能出 `workspace`、表达式不能带函数调用、指数不能太大，这些都得在工具层做死，
不能指望提示词。另外离线模式是被逼出来的：因为演示不一定有网，只好把常见说法一条条写成规则，
写的过程反而让我想清楚了"这个助理到底该会哪几件事"。

**邓家俊**：我主要做需求梳理和测试走查。最大的感受是"能说"和"会做"之间最容易出问题的是**参数**：
用户说"读一下那个文件"，模型可能给出一个不存在的路径，或者干脆忘了给文件名。
所以工具遇到参数不对时必须说清楚哪里不对，不能只回一个"失败"。
另外走查网页界面时发现，把每次调用的工具显示出来特别有用——用户能看见它到底做了什么，信任感完全不一样。

## 八、踩过的坑和后续计划

踩过的坑：

* MCP 服务一开始用 `sys.stdin.readline()` 读，Windows 控制台编码会把中文参数弄坏，
  改成 `sys.stdin.buffer` 按 UTF-8 字节读写才稳定；
* 离线规则一开始把"帮我查一下北京的天气"里的城市识别成了"北京的"，后来把贪婪匹配改成非贪婪，
  再补了一层前后缀清理；
* 记忆文件写失败会让整次对话崩掉，后来改成"记忆写入失败只影响记忆"。

后续想做：语音输入输出、把工具拆成独立的 MCP 服务（比如单独一个文件服务）、
以及给网页界面加上工具调用历史的持久化。
